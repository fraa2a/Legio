# Artwork Priority and Cache Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Bound artwork work, prioritize the opened game, and refresh cached content only on game-page opening without blanking existing content.

**Architecture:** A Rust scheduler controls network and conversion admission while existing caches and resource locks retain deduplication. Frontend services manage consumer lifetime, declare selection before page animation, and publish decoded replacement generations. Cache reads are immediate and independent of scheduled refresh.

**Tech Stack:** Rust 1.98.1, Tokio, existing reqwest/SQLite/image/WebP/UUID dependencies, Tauri 2, Svelte 5, Node 22 test scripts.

**Spec:** [Approved design](../specs/2026-10-11-artwork-priority-cache-and-rendering-design.md).

## Global Constraints

- Remain on `feat/store-filters-release-0.2.0`, version `0.2.0`; PR #183 remains draft until Windows acceptance.
- Maximum five artwork-related network operations, with four available to ordinary work; maximum two conversions, with one ordinary admission slot.
- Metadata freshness is three days; artwork freshness is five days; stale existing entries refresh only on game-page opening or explicit refresh.
- Preserve cached content until a validated replacement is ready; use five-minute failed-refresh backoff for automatic retries.
- Rust owns scheduling and disk operations; Tauri commands remain thin and artwork futures boxed, with a 4096-byte release-profile size budget.
- Application/network logs remain independent, opt-in and disabled by default. No sensitive paths/URLs, per-frame noise, new dependencies or unsafe code.
- Preserve existing cache formats and bounded storage policies. No TaxLauncher migration or release merge in this plan. Git metadata/documentation use English and no em/en dashes.

## Review Focus

- Rapid game A/B/A selection while the urgent network slot is occupied: the latest game starts, canceled transfers leave no partial entry, and reusable work resumes. Task 1.
- Two consumers share an image but only one remains mounted during replacement: the remaining old-generation URL stays valid until its release. Task 4.
- WebView reload or abandoned publication: a staged replacement must not erase the last valid persistent image or leak capacity/files. Tasks 1 and 3.
- A metadata URL or language changes before artwork expiry: metadata updates without prematurely replacing artwork, while screenshots remain keyed to valid resource identities. Tasks 2 and 4.
- Cache pruning, corrupt entries or disk-write failure during refresh: limits remain bounded and the last usable image survives; warnings remain actionable. Task 3.

## File Map and Execution Order

Create `src-tauri/src/artwork_scheduler.rs` for admission, selection and request lifetime; `src-tauri/src/artwork_publication.rs` for staged replacement ownership; `src/lib/services/artwork-work.ts` for IPC consumer/selection lifetime; and `scripts/test_artwork_work.mjs` for that service's behavioral tests. Modify existing asset/details services rather than moving the whole pipeline. Register native state and commands in `src-tauri/src/lib.rs` and `commands.rs`.

Modify `steam_details.rs`, `steam_assets.rs`, `steam_pics.rs`, and the frontend details/image services for refresh policy and integration. Extract the metadata service into `src/lib/services/steam-metadata.ts` so image requests can resolve metadata without importing the metadata store and introducing a circular dependency. Update `SteamArtwork.svelte`, `GameDetailView.svelte`, `StoreGameCard.svelte`, `ArtworkTile.svelte`, `ScreenshotGallery.svelte`, `ArtworkViewer.svelte`, `library-artwork.ts` and `App.svelte` only where they declare demand or display lifecycle. Extend existing scripts and CI test invocation. Implement Tasks 1-5 in order; execute the independent rendering plan separately afterward.
